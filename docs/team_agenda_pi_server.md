# Pi ↔ 서버 연동: 팀 상의 안건

> 작성: 2026-11-18 · 작성자: 수꽝 · 대상: AI·IoT 파트(Pi), 떵개(지도 데이터)
> 근거: `psubin05/SPASIBA` `raspberrypi` 브랜치(커밋 `816b608`, 11/17)의 `src/edge_cloud/`와 `docs/EDGE_CLOUD_IMPLEMENTATION.md`, 서버 인터페이스 명세 v0.3.1
> 서버와 주고받는 형식(토픽, event 필드, status·LWT, 재전송 규칙, crop 크기)은 Pi 구현과 대부분 맞습니다. 아래는 **한쪽만 정할 수 없어서 같이 정해야 하는 것**입니다.

## 안건 1. 이벤트 발행 조건과 빈 칸 판단 (AI·IoT)

**현재 Pi 동작**
- 칸 상태는 `UNKNOWN` / `OCCUPIED` / `EMPTY` 세 가지이고, 처음에는 `UNKNOWN`입니다.
- `UNKNOWN`이면 이벤트를 발행하지 않습니다. `OCCUPIED`이거나, 설정에 `"publish_on_consensus": true`가 있을 때만 발행합니다.
- 그런데 실제 실행 코드(`pi_camera.py`)에는 칸을 `OCCUPIED`나 `EMPTY`로 바꾸는 부분이 없습니다. 정차·빈 칸 판단은 아직 구현되지 않았다고 Pi 문서에도 적혀 있습니다.

**생기는 문제**
1. **기본 설정으로는 이벤트가 하나도 나가지 않습니다.** 통합 테스트·리허설에서는 `publish_on_consensus: true`를 켜야 합니다.
2. **같은 차가 같은 칸에 다시 대면 이벤트가 나가지 않습니다.** Pi는 칸별 마지막 번호를 기억하고, `EMPTY`가 되어야 그 기억을 지웁니다. 빈 칸 판단이 없으니 기억이 계속 남습니다.
   - 예: `12가3456`이 B2-A-03에 주차 → 출차 → 다시 입차해서 또 B2-A-03에 주차
   - 서버는 출차 때 배정을 끝냈으므로, 새 입차 세션은 칸을 못 찾고 계속 `PENDING`(위치 확인 중)으로 남습니다.

**정할 것**
- [ ] 리허설·시연에서 `publish_on_consensus: true`로 운영할지
- [ ] 빈 칸(`EMPTY`) 판단을 이번 프로젝트에서 구현할지. 안 한다면 아래 중 무엇으로 대신할지
  - (가) 시연 시나리오에서 "같은 차가 같은 칸에 다시 주차"를 빼기 (가장 간단)
  - (나) 번호판이 일정 시간(예: N분) 계속 안 보이면 `EMPTY`로 보기. 단, Pi 문서는 "미검출은 빈 칸 근거가 아니다"라고 보고 있어 오판 위험을 같이 따져야 함
  - (다) 서버가 출차를 처리할 때 그 칸의 Pi에 "기억 지우기" 메시지를 보내기 (토픽을 새로 만들어야 함)
- [ ] 정차 판단(지나가는 차 구분)을 어떻게 할지. 지금은 투표 5표 이상이면 정차로 보는 셈

**수꽝 제안:** 시연 기간에는 `publish_on_consensus: true` + (가). 시간이 남으면 (다)를 검토.

## 안건 2. crop 요청·응답 조건 (AI·IoT)

**현재 Pi 동작**
- crop 기능은 기본으로 꺼져 있습니다 (`crop_enabled: false`).
- 켜면 이벤트를 만들 때 **칸마다 마지막 사진 1장**을 메모리에 보관합니다 (기본 10분, `crop_ttl: 600`).
- 서버 요청의 `slot_id`와 `event_id`가 **그 칸의 마지막 이벤트와 정확히 같을 때만** 응답합니다.
- 다음 경우에는 **아무 응답도 보내지 않고** Pi 로그에만 남깁니다.
  - 요청한 `event_id`가 마지막 이벤트가 아님 (그 사이 새 이벤트가 생김)
  - 10분이 지남
  - Pi가 재시작해서 메모리가 비었음
  - 요청에 `event_id`가 없음

**서버 쪽 영향**
- 서버는 매칭 보류 120초 뒤 crop을 요청합니다. 요청할 때는 **그 칸의 가장 최근 `event_id`** 를 넣겠습니다.
- 응답이 없으면 서버는 "사진 없음"을 알 방법이 없어 기다리기만 합니다. 그래서 서버는 **정해진 시간 안에 응답이 없으면 사진 없이 관리자 확인**으로 넘기겠습니다.

**정할 것**
- [ ] 이번 프로젝트에서 crop 기능을 켤지 (`crop_enabled: true`)
- [ ] 보관 시간 10분이 충분한지. 서버는 보류 120초 뒤 요청하므로 보통은 충분하지만, 관리자가 늦게 볼 때 다시 요청하는 경우는 실패함
- [ ] 사진을 못 줄 때 "없음" 응답을 보낼지. 보낸다면 형식 예: `{"request_id": "…", "error": "expired"}` 를 같은 `crop` 토픽으로
- [ ] 서버가 기다릴 시간 (수꽝 제안: 10초)
- [ ] 관리자 확인이 끝나거나 출차했을 때 Pi의 사진도 지울지 (지금은 10분 뒤 요청이 올 때 만료 처리만 함)

**수꽝 제안:** crop 켜기, `event_id` 필수, "없음" 응답은 보내 주면 좋지만 없어도 서버가 10초 뒤 넘기도록 처리.

## 안건 3. 칸 목록이 Pi와 서버에서 어긋나는 문제 (AI·IoT, 떵개)

**현재 상태:** 칸 목록을 **두 곳에서 따로 손으로 관리**합니다. 두 목록을 자동으로 맞춰 주는 장치는 없습니다.
- **Pi 쪽:** Pi 팀이 카메라 설정 파일(`edge.example.json`의 `single_slot`이나 `rois`)에 칸 ID를 직접 적습니다.
- **서버 쪽:** 떵개가 지도 데이터(`parking_slot`)에 칸 ID를 직접 넣습니다.

**어긋나는 경우**

| 경우 | 예 |
|---|---|
| 오타 | Pi 설정은 `B2-A-7`이나 `B2-A-O7`이고, 서버는 `B2-A-07` |
| 번호 매기는 방식이 다름 | Pi 팀은 왼쪽부터 01, 02…로 매기고, 떵개는 오른쪽부터 매김 |
| 한쪽만 고침 | 리허설 중에 카메라 위치를 옮겨서 Pi 설정만 B2-A-08로 바꾸고 지도 데이터는 그대로 둠 |
| 아직 등록 전 | Pi를 먼저 테스트하는데 서버 지도 데이터에는 그 칸이 아직 없음 |
| 예시값을 그대로 씀 | Pi 설정 예시의 `B2-A-01`, `B2-A-02`는 실제 등록값이 아니라고 Pi 문서에도 적혀 있음 |
| ID 형식 변경 | 카메라 ID 형식 변경처럼 규칙이 바뀌는 도중에는 한쪽만 먼저 바뀌기 쉬움 |

시연 준비 기간에는 카메라 위치와 칸 배치를 여러 번 바꿀 테니, 한 번쯤은 거의 확실히 생깁니다.

**서버의 대응 (수꽝이 처리)**
- DB가 등록 안 된 칸의 이벤트를 거부하면 "Pi는 보냈다는데 서버에는 없다"는 상황이 되어 원인을 찾기 어렵습니다.
- 그래서 서버는 이런 이벤트도 **저장은 하되** `valid=false`, `invalid_reason="등록 안 된 칸"`으로 표시하고 매칭에는 쓰지 않겠습니다. DB만 조회해도 원인이 보입니다.

**정할 것**
- [ ] 칸 번호 매기는 규칙 (어느 쪽 끝부터 01인지, 기준 그림)
- [ ] 카메라별 담당 칸 목록의 **원본을 어디에 둘지** (예: 떵개의 지도 데이터 파일 하나를 원본으로 하고, Pi 설정은 거기서 복사)
- [ ] 카메라 위치·칸 배치를 바꿀 때 누가 누구에게 알리는지
- [ ] (선택) 근본 해결: Pi가 시작할 때 서버에서 자기 칸 목록을 받아 오기. Pi 쪽 작업이 늘어나므로 지금은 보류 제안

## 안건 4. 카메라가 구역에서 떨어지면서 지도 데이터에 생기는 영향 (떵개)

인터페이스 v0.4에서 카메라를 구역에서 떼어 냅니다 (카메라 한 대가 여러 구역의 칸을 볼 수 있음, 아래 참고). 지도 데이터는 떵개 담당이므로 서버 쪽은 바꾸지 않고, 아래를 떵개가 정해 주면 거기에 맞춥니다.

**서버가 지도 데이터에서 읽기만 하는 것**
- 이벤트의 `slot_id` → `parking_slot.zone_id`로 구역 찾기 (이벤트에서 `zone_id`가 빠지므로)
- 이벤트의 `slot_id`가 `parking_slot`에 있는지, 그 칸의 `camera_id`가 보낸 카메라와 같은지 (등록 칸 검사)

**정할 것**
- [ ] `camera` 테이블의 `zone_id`를 어떻게 할지 (예: `floor`로 바꾸기, 또는 그대로 두되 "대표 구역" 정도로만 쓰기)
- [ ] 카메라 ↔ 칸 연결을 `parking_slot.camera_id` 하나로 표현할지 (칸 하나를 카메라 두 대가 보는 경우가 있는지)
- [ ] 새 `camera_id` 형식 `CAM-B2-01`을 지도 데이터에도 쓸지

## 참고: 함께 알릴 예정 변경 (인터페이스 v0.4, 문서 확정 후 별도 공지)

- MQTT 토픽에서 구역을 뺍니다: `spasiba/{zone_id}/{camera_id}/…` → `spasiba/{camera_id}/…`. 카메라 한 대가 여러 구역의 칸을 볼 수 있기 때문입니다.
- `camera_id` 형식: `CAM-B2-A-01` → `CAM-B2-01` (층 + 번호).
- 이벤트의 `zone_id` 필드는 빠집니다 (서버가 `slot_id`로 구역을 찾음. 보내도 무시).
- 번호판 형식 검사는 Pi 기존 OCR 코드의 용도 문자 목록(`USE_CHARS`)으로 통일합니다. 서버와 인터페이스 문서를 Pi 쪽에 맞춰 고칩니다.
- Pi 쪽에서 바꿀 곳(예상): 토픽 앞부분, `status_topic` 설정, `config.py`의 카메라 ID 형식 검사와 "칸이 카메라 구역에 속하는지" 검사.
