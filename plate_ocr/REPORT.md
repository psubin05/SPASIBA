# 번호판 OCR — 진행 보고

작성: 2026-10-18

## 1. 개요

AI Hub 차량 데이터로 번호판 글자 인식(OCR) 모델을 구축하였다. 데이터 확보부터 학습 데이터 생성, 모델 학습, 평가까지 전 과정을 수행하였으며, 한국어 사전학습 모델을 파인튜닝하여 **테스트 7,030장에서 번호판 단위 전체 일치 97.91%, 글자 오류율 0.42%** 를 달성하였다.

담당 범위는 아래 파이프라인의 ③ 글자 인식이다. 번호판 검출기는 학습하지 않고 기존 가중치를 데이터 준비에만 사용하였다.

```
AI Hub 사진
   ↓
① 번호판 검출 (crop)        학습하지 않음
   ↓
② 줄 검출 + 두 줄 펴기       PP-OCRv5 mobile det
   ↓
③ 글자 인식  ← 담당 범위     TrOCR 파인튜닝
   ↓
번호 문자열
```

### 현재 상태

| 항목 | 상태 |
| --- | --- |
| AI Hub 데이터 확보 | 완료 — 90,000장 + 라벨 90,000개 |
| 학습 데이터 생성 | 완료 — 68,885장 (train / val / test) |
| 데이터 누수 점검 | 완료 — 세 split 간 번호 교집합 0 |
| 모델 학습 | **완료** — 3 epoch, 26.6분 |
| 테스트 평가 | **완료** — 7,030장, 97.91% |
| 형식 보장 디코더 | 구현 완료 |
| 확신도 곡선 | 미착수 |
| 강건성 평가 | 미착수 |

## 2. 데이터셋 구축

### 2-1. AI Hub 선별 다운로드

데이터셋 `103.자동차 차종-연식-번호판 인식용 데이터` (datasetkey 172, 전체 231 GB) 중 OCR에 필요한 **1.4 GB만** 선별하였다. 나머지 230 GB(차종분류 8 GB, 원본 프레임 222 GB)는 검출기 학습용이므로 받지 않았다.

| 파일 | 내용 | 용량 | filekey |
| --- | --- | --- | --- |
| 자동차번호판OCR_training.zip | 라벨 JSON | 21 MB | 49029 |
| 자동차번호판OCR_validation.zip | 라벨 JSON | 3 MB | 48958 |
| 자동차번호판OCR데이터.zip (Training) | 이미지 | 1 GB | 48946 |
| 자동차번호판OCR데이터.zip (Validation) | 이미지 | 142 MB | 48960 |

리눅스에서는 홈페이지의 INNORIX 다운로드 프로그램이 설치되지 않으므로 공식 CLI를 사용하였다.

```bash
curl -o aihubshell https://api.aihub.or.kr/api/aihubshell.do && chmod +x aihubshell
./aihubshell -mode l -datasetkey 172
./aihubshell -mode d -datasetkey 172 -filekey 49029,48958,48946,48960
```

결과: 이미지 90,000장 / 라벨 90,000개, ZIP 4개 모두 무결성 검사 통과.

### 2-2. 데이터 누수 차단

AI Hub는 같은 차량을 여러 장 촬영하였다. 번호 39,343개에 사진 89,251장으로 번호당 평균 2.27장이며, 한 번호는 **최대 166장**까지 존재한다. 두 가지 누수 위험을 확인하고 차단하였다.

**(1) AI Hub가 제공한 Training / Validation 구분을 그대로 사용할 수 없다**

```
Training 36,787개  ∩  Validation 7,578개  =  4,710개 겹침
```

Validation 번호의 **62%가 Training에도 존재**한다. 이 구분을 train/test로 쓰면 그 자체가 누수가 된다. 두 폴더를 합친 뒤 다시 분할하였다.

**(2) 사진 단위 분할은 같은 차량을 양쪽으로 쪼갠다**

사진 166장을 가진 번호를 8:1:1로 나누면 같은 차량의 다른 사진이 train과 test에 동시에 들어가, 차량을 외운 모델이 높은 점수를 받는다. **번호 문자열 단위**로 분할하였다.

```python
def split_of(value):
    h = int(hashlib.sha1(value.encode()).hexdigest(), 16) % 10
    return "test" if h == 0 else "val" if h == 1 else "train"
```

난수나 시드가 없는 순수 함수이므로, 같은 원본만 있으면 누구든 동일한 분할을 재현할 수 있다.

### 2-3. 학습 데이터 생성

```
원본 사진
   ↓ 검출기로 번호판 박스 (확신도 1등, 사방 4% 여백)
번호판 crop
   ↓ PP-OCR det으로 글자 영역 검출 → 로고·작은 글씨 제거 → 줄 묶기
줄 박스 1~2개
   ↓ 2줄이면 윗줄·아랫줄을 같은 높이로 맞춰 좌우로 이어 붙임 (펴기)
높이 48 이미지 + 번호 라벨
```

한 줄/두 줄을 따로 분기하지 않는다. crop 안의 글자는 전부 한 번호판이므로 두 줄이면 펴서 한 번에 읽는다. AI Hub 라벨에 줄 정보가 없어 줄별 정답을 만들 수 없고, 줄을 나눠 두 번 읽으면 실패 확률이 두 배가 되기 때문이다.

| | 장수 | 일반 1줄 | 일반 2줄 | 지역명 1줄 | 지역명 2줄 |
| --- | --- | --- | --- | --- | --- |
| train | 54,991 | 42,762 | 392 | 8,317 | 3,520 |
| val | 6,864 | 5,318 | 54 | 1,054 | 438 |
| test | 7,030 | 5,488 | 48 | 1,023 | 471 |

누수 점검: train ∩ val = 0, train ∩ test = 0, val ∩ test = **0개**

지원 형식 89,251장(일반 61,927 / 지역명 27,324), 제외 749장(`경기부천아5…` 형태의 구형 시·군 번호판)

## 3. 모델

### 3-1. 선정

**`team-lucid/trocr-small-korean`** (Hugging Face, **Apache 2.0**)

학습 데이터는 5.5만 장이다. 한국어 텍스트로 대규모 사전학습된 인식기를 가져오면 글자 모양에 대한 지식을 훨씬 많이 확보할 수 있다고 보았다. 특히 번호판 오답의 상당수가 **생김새가 비슷한 한글**(`어↔고`, `모↔오`, `나↔너`)이라, 이 부분에서 사전학습이 유효할 것으로 판단하였다.

| 항목 | 값 |
| --- | --- |
| 파라미터 | 54,541,824 |
| 구조 | DeiT 인코더 + RoBERTa 디코더 (자기회귀) |
| 사전학습 | SynthTIGER 합성 한국어 **600만 장** |
| 입력 | 384 × 384 |
| 라이선스 | Apache 2.0 |

검토한 다른 후보:

- **PARSeq** — 사전학습 문자집합에 한글이 없어 이점이 사라진다
- **ddobokki/ko-trocr** (214M) — AI Hub 데이터로 학습되어 **테스트 세트와 겹칠 위험**이 있어 제외

### 3-2. 토크나이저 적합성 확인

학습 전에 테스트 7,030개 번호를 전부 인코딩 후 디코딩하여 **손실 0개**를 확인하였다.

```
18라3723      → ['18', '라', '37', '23']
인천70바6022   → ['인천', '70', '바', '60', '22']
```

숫자·한글 용도기호·지역명이 모두 어휘에 존재하며, 특히 **지역명이 토큰 하나로 묶인다.**

### 3-3. 학습

약한 증강만 적용하여 3 epoch 학습하였다. 사전학습 모델이므로 긴 커리큘럼이 필요하지 않았다.

| 설정 | 값 |
| --- | --- |
| epoch | 3 |
| batch | 12 |
| 학습률 | 5e-5, AdamW + OneCycleLR |
| 증강 | perspective 0.04, 회전 ±4°, blur 15%, 밝기·대비 |
| 환경 | RTX 3070 Ti Laptop 8GB, AMP |
| 소요 | **26.6분** |

epoch별 검증 정확도는 다음과 같다.

| epoch | 검증 전체 일치 | 검증 CER | 누적 시간 |
| --- | --- | --- | --- |
| 1 | 92.08% | 1.73% | 8.5분 |
| 2 | 97.08% | 0.54% | 17.4분 |
| **3** | **98.08%** | **0.35%** | 26.6분 |

**1 epoch 만에 92%에 도달**하였다. 사전학습으로 한글 글자 모양을 이미 알고 있어, 번호판 도메인에 맞추는 적응만 필요했기 때문이다.

## 4. 평가 결과

테스트 7,030장(학습에 사용하지 않은 번호)

| 종류 | 장수 | 전체 일치 | 글자 오류율 |
| --- | --- | --- | --- |
| **전체** | 7,030 | **97.91%** | **0.415%** |
| 일반 1줄 (`12가3456`) | 5,488 | 98.07% | 0.379% |
| 지역명 1줄 (`서울31자1234`) | 1,023 | 97.36% | 0.576% |
| 지역명 2줄 (`경기71 아3595`) | 471 | 98.09% | 0.236% |
| 일반 2줄 (초록 구형 `02마 3502`) | 48 | 89.58% | 2.360% |

측정 단위는 **번호판 1장**이다. 두 줄 번호판을 줄 단위로 세면 같은 모델도 더 높게 나오므로 줄 단위 수치는 사용하지 않았다.

**지역명 두 줄(471장)이 98.09%로 전체 평균을 웃돈다.** 지역명을 토큰 하나로 다루는 사전학습 토크나이저의 특성이 유효하게 작용한 것으로 보인다.

**가장 약한 구간은 초록 구형 두 줄(89.58%)이다.** 학습 데이터가 392장뿐이고, 펴진 두 줄 번호판은 가로로 매우 길어 384×384 정사각 입력에서 세로로 크게 늘어난다. 다만 테스트 표본이 48장이라 신뢰구간이 넓다.

## 5. 형식 보장 디코더

### 5-1. 내용

한국 번호판은 형식이 고정되어 있다.

```
일반   : 숫자{2,3} 한글 숫자{4}          12가3456, 123가4567
지역명 : <지역> 숫자{1,3} 한글 숫자{4}    서울12가3456, 서울4도9472
```

일반적인 CTC 디코딩은 이 규칙을 알지 못해 `1112222`(한글 없음)나 `08누596`(자릿수 부족)처럼 번호판으로 성립할 수 없는 출력을 낸다. 이를 막기 위해 번호판 문법을 **유한상태 기계**로 구현하고, CTC prefix beam search가 각 상태에서 허용되는 토큰만 이어붙이도록 하였다.

```
상태 = (지역명 사용, 한글 앞 숫자 개수, 한글 지나감, 한글 뒤 숫자 개수)
수용 = 한글 뒤 숫자가 정확히 4개
```

### 5-2. 검증

문법 단독 검사 12케이스를 모두 통과하였다.

| 입력 | 판정 |
| --- | --- |
| `12가3456`, `123가4567`, `서울4도9472`, `경기12가3456` | 허용 |
| `08누596`, `88다027`, `1가3456`, `1234가5678`, `12가34567`, `가12345` | 거부 |

CTC 특성상 반복 글자(`333주6697`)가 여러 프레임에 걸쳐 나타나는 경우를 별도로 처리하였다. 같은 접두사에 흡수하는 동작은 글자 수를 늘리지 않으므로 문법 제약 대상에서 제외해야 한다.

### 5-3. 의의

**번호판으로 불가능한 문자열이 출력되지 않는다.** 서버에서 입차 차량 후보와 대조할 때 형식이 보장된 입력만 들어오므로 처리가 단순해진다. 추가 학습 비용은 없다.

## 9. 한 문장 정리

**AI Hub 차량 데이터 중 OCR에 필요한 1.4 GB를 선별 확보하고 번호 단위 분할로 데이터 누수를 차단한 학습 세트 68,885장을 구축한 뒤, 한국어 600만 장으로 사전학습된 외부 모델(Apache 2.0)을 3 epoch 파인튜닝하여 테스트 7,030장에서 번호판 단위 전체 일치 97.91%·글자 오류율 0.42%를 달성하였으며, 번호판 형식을 보장하는 디코더를 함께 구현하였다.**
